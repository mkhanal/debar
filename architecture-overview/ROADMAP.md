# Roadmap

The pieces Debar is built from, their order, and what exists today. Each piece gets its own design, requirements and build, and ends with something measured or compared.

## What exists today

- The governing documents in this repository.
- The study folder for the first signature format, with its reference scanner and databases pinned and a first set of notes.
- The toolchain image (`toolchain.Dockerfile`) and `./in-toolchain`, which runs any command in it, locally as in CI.
- A Cargo workspace on Rust 1.100.0 with the `xtask` crate and slices 1 to 6 of pieces 3 and 4: hash signatures, extended signatures of every target, file typing, logical signatures with their regular-expression (backreferences and lookaround among them), byte-comparison and image fuzzy hash subsignatures, and container signatures, end to end; and certificate rules, icon signatures, URL rules, engine switches and signature programs compiled into the image for the pieces that use them:

  - `debar-image`: the format-neutral model for hash and pattern signatures and the image: header, section directory and checksums, front-coded names, one hash table per purpose, category and algorithm with its size directory and a binary fuse filter probed in place, one pattern section per signature group holding a hashed four-byte anchor filter, a two-byte filter, anchor tables, placed signatures (from the start, before the end, or at an entry point, a section or version information in an executable) and verification programs, Debar's own `ObjectKind`, an object-kinds section mapping each kind to its signature groups and its typing data, a type-magic table, a logical-signature section per group (postfix expressions, count ceilings, conditions), the categories of potentially unwanted signatures, a filter per set of selected groups, a section per group of regular expressions (with their triggers and their forward and reverse automata, or their text where the automata would be large), byte comparisons and a sorted table of image fuzzy hashes, a section of container signatures with their entry-name automata, the format-neutral tree of a regular expression and its backtracking program, a set of Debar's own engine features, certificate rules, icon signatures in their groups, URL rules with their automata, and a format-neutral section of verified signature programs, all read in place or decoded on demand.
  - `debar-clamav-signatures`, the first signature-format part: signed and unsigned containers, verified by their detached or header signature and their signed index, hash files, ignore lists, extended signature files of every target with every offset form, logical signature files with their target description, expression, modifiers and regular-expression (translated by the part into the engine's syntax tree), byte-comparison and image fuzzy hash subsignatures, container signature files, the file-type database, certificate rule, icon, URL-rule and switch files, and signature programs checked as the reference checks them, with their triggers as logical signatures, with an account of every line of every database file. It writes each target's group, the reference's window overlap per group (counting logical-signature parts it does not yet compile), the reference's memory of nine part ends, and for a hash key listed more than once only the name the reference reports.
  - `debar-compiler`, which compiles a folder of databases into an image and an account report.
  - `debar-matching`: which digests an object needs, whole-file and section lookups, false-positive trust, and a streaming pattern scan (`feed` and `finish`) over the groups an object kind selects, with look-back, executable placements resolved against an `ExecutableLayout` asked for only for executables, type-recognition outcomes, and detections ordered as the reference reports them; logical signatures counted, gated on their rarest subsignatures with a second pass for the armed ones, and evaluated with their conditions; potentially unwanted detections filtered by setting and category; regular expressions, byte comparisons and image fuzzy hashes matched after the walk over the whole object (held whole up to 4 MiB, read through a 4 MiB page pool above it), the regular expressions in linear time, or by Debar's own bounded backtracking matcher where a linear engine cannot express them, and only up to a size limit; program triggers reported apart from detections; and the container signatures an archive entry's facts satisfy (`container_entry_detections`), tested with synthetic entries until the archive modules exist.
  - `debar-scan`, the scan core so far, for the top-level object: one scan per file with a stack of layers (only the top level is pushed yet) holding ordered evidence, a ledger counting the top level against the file-count and scan-size limits, the minimum size and the top-level file-size limit, typing from the first bytes and re-typing after the full scan, the own-bytes pattern scan read through `ObjectBytes`, and a second full pass as the kind the image names for binary data, compiled Python and AI models, chosen by the kind typed from the first bytes, in 128 KiB chunks with the whole-object digests taken on the same read, hash and logical detections, false-positive trust checked on every alert for the layer and every layer above it, first-match (the default) and every-match, potentially unwanted detections deferred to the end, heuristic precedence, and a `ScanReport` that always comes back (verdict, reported detections in the reference's order, completion, limits reached), with an `ObjectObserver` told of each finished object.
  - `debar-interfaces` with `debar comparison-report`, which scans one file through the scan core and writes the comparison harness's report of each object it finished, stopping at the first strong detection unless `--every-match` is given, with `--heuristic-precedence` and `--largest-regular-expression-object`; and `debar measure-scan`, which measures throughput through the scan core.
  - `acceptance`, outside the product, whose tests prove the requirements in `specs/` by running Debar's commands as a user would, with `acceptance/best-scan-speed.json`, the throughput ratchet's records, and `scan-profile`, which reports where a scan's instructions go, stage by stage, on every corpus kind.

Miri runs on the platform crate on every change.
- `cargo xtask release-check`, which fails while "Borrowed pieces" lists anything.
- Work tracked as claimed GitHub issues on the "Debar" board, with the skills in `.claude/skills/` (catalogued in `.claude/README.md`) and the board tasks `cargo xtask claim`, `check-claim`, `classify-work`, `record-pull-request-size`, `ready-for-review`, `claim-next`, `hand-back` and `issue-brief`.
- Requirements in `specs/` for hash, pattern and logical detection (regular expressions with backreferences and lookaround, their size limit and byte comparisons among them), file typing, the accounting of every line of the pinned databases with none left uncompiled, their verification by digital signature and the refusal of one that does not verify, an image identical across runs and architectures, readiness within 50 ms, private memory within 64 MiB, at least twice the reference's throughput and never less than the best throughput recorded for each corpus kind, each passing on every change. On the pinned databases: 3,647,104 lines compiled into a 496 MB image in 20.3 s, among them 3,212,354 hash signatures, 105,901 pattern signatures, 322,396 logical signatures, 133 container signatures, 256 file-type lines, 30 certificate rules, 222 icon signatures, 448 URL rules and 82 signature programs; start, readiness and a small scan in 4,108,274 instructions; 8 KiB of the image resident (from a cold cache) and 168 KiB private memory once ready; 4.7 to 7.8 times the reference's single-threaded throughput on every corpus kind.
- **Piece 4 is done** for raw bytes: the comparison passes on every push, judged by the harness's ratchets, and the throughput budget and its ratchet are requirements whose tests pass on every change. What the reference matches only after a parser or normaliser has run, and `HandlerType` re-scans, come with pieces 5 and 6.

What the carried sections are for is built with their pieces: Authenticode and icon matching and the phishing check (piece 6), running signature programs (piece 7).

## The pieces, in order

| # | Piece | It is done when |
| --- | --- | --- |
| 1 | **Foundation** | The reference is pinned, the study notes hold an inventory of everything the reference scanner does, and the workspace builds, lints and tests an empty crate with every check below in place |
| 2 | **Comparison harness** | One command runs the reference scanner and Debar on the same input and reports any difference in what each extracted and what each detected, failing only on differences not already known. It can build a matching input from a signature, proved against the reference scanner. Until Debar can scan, its side is proved against a stand-in |
| 3 | **Signature compiler** | Every database file of the format compiles into an image, every signature in the pinned databases is accounted for in it, and the start-time and memory budgets are requirements whose tests pass on every change |
| 4 | **Matching engine** | Given raw bytes, it reports the same signatures the reference scanner does, and the scan-speed budget is a requirement whose test passes on every change |
| 5 | **Scan core** | A file of a kind needing no format module is scanned end to end with the reference scanner's limits and verdicts, within every budget |
| 6 | **Format modules** | Each module matches the reference scanner on its own inputs in the harness, within every budget, and records the facts native mode reports as findings. Built one at a time, the most common formats first |
| 7 | **Signature programs** | Signatures that are programs run and produce the reference scanner's detections |
| 8 | **Updater and live update** | Published databases are fetched, verified and compiled, and a running scanner switches image with no scan lost and within the memory budget |
| 9 | **Interfaces** | Native mode is complete, with its findings, refusals, whole-file reach and confinement, and compatibility mode passes for every command, protocol message and configuration option of the scanner being replaced |
| 10 | **Signature sources** | A deployment chooses its sources by configuration; the updater fetches and verifies each by its own rules and refuses a source whose terms forbid how it is used; every chosen source compiles into one image, and each detection names its source. Third-party sets in an already supported format load through that format's part, compared with its reference scanner loading the same files |
| 11 | **A second signature format** | A format with a public ecosystem of rules beyond the first is a part of its own, with its own pinned reference scanner, study folder and harness, matching that reference on its own inputs, and selectable as a source |
| 12 | **Hash and indicator feeds** | Published lists of known-bad hashes and similar indicators are sources, compiled into the image's hash tables, checked by lookup, and refreshed on the feed's own cadence |

Pieces 10 to 12 come after the first release. Pieces 1 and 2 come first whatever else changes: every later piece is checked against the notes and the harness.

## The performance track

Speed is a standing track beside the pieces, not a final slice (DECISIONS, "Aim for fifty times the reference's speed"). The aim is fifty times the reference on every corpus kind; each kind's best figure is a ratchet that only tightens. Each step profiles the stages with `scan-profile`, pulls the lever the profile shows is largest, records the before and after in DECISIONS and lowers the records.

- **Done:** the ratchet, the stage profile, a call-free prefilter (86 to 93 instructions per byte down to 31 to 38), a second pass searched through a filter instead of an automaton built per scan (about 40 per byte down to 7 to 12), and cheaper verification (23 to 39 down to 9 to 26).
- **Next, by the last profile:** digests (40 per byte on every kind; SHA-256 in hardware behind a safe platform primitive, open item A13), the prefilter (31 to 38), on real PDFs a linear-time check before the backtracking matcher (51 per byte there), the cost per anchored candidate on executables, placing the signatures tied to offsets on every object, copying each chunk into the retained buffer, and parallel scanning of independent objects.

## Evidence for the same detections

No test can cover every possible file, so Constitution §1 rests on three kinds of evidence together:

- **Each pattern signature** is checked with a matching input built from the signature itself.
- **Each hash signature** is checked by lookup.
- **Large collections of real files**, clean and malicious, are run through the reference scanner and Debar, and compared object by object.

## Candidates under consideration

Ideas for inside the layers. None is decided; each is settled in the design of its piece and recorded in [DECISIONS.md](./DECISIONS.md).

- **Signatures as a compiled program.** The compiler sees every signature at once and groups them by the facts they require, so the engine selects the applicable set from an object's facts before matching any bytes.
- **Work on demand.** A fact is computed only when a live signature asks for it.
- **Streaming with fixed memory per scan.** Content flows through matching as it is produced, with no temporary files, except where a signature needs random access.
- **Hashes behind a small in-memory filter.** The full table stays on disk and is touched only when the filter says a hash may be present.
- **Signature programs compiled ahead of time**, when the image is built.
- **The image laid out by hand and read in place** with `zerocopy`, with no validation pass at start.
- **Our own matcher**: a literal prefilter laid out in the image as a double-array automaton, then verification of wildcards and gaps. `daachorse` and `aho-corasick` are the measured starting points.
- **Hand-written readers** for scanned formats over the input gate, so a damaged file is handled as the reference scanner handles it.
- **A binary fuse filter** in the image in front of the hash tables.
- **An interpreter for signature programs**, with their bytecode checked and lowered when the image is built.
- **A fixed thread pool** for the daemon, with blocking I/O through the gates, instead of an async runtime.
- **mimalloc and an arena per scan**, kept only if they measure better (the performance track).
- **Compile once, map everywhere.** The updater is the only thing that compiles; every scanner process maps the same image.

## Checks to build

Rules that are written down but not yet enforced by a machine. Each is removed from this list when it runs on every change.

- Every format module is fuzzed (Constitution §8). `cargo xtask fuzz` runs every fuzz target for 30 seconds on every change; ClusterFuzzLite, with longer runs weekly, arrives with the first format module.
- Audits of every dependency with cargo-vet. The tool is in the toolchain image; the audit set is started with the first dependency linked into a release.
- Mutation testing with cargo-mutants and coverage with cargo-llvm-cov, weekly. Both tools are in the toolchain image.
- Resource budgets (Constitution §12) gated on allocation counts and proportional set size. Start time and throughput are gated on instruction counts and memory on private and resident bytes read from `/proc`.
- No release while "Borrowed pieces" has an entry (Constitution §13): `cargo xtask release-check` exists and runs in the release workflow, which comes with the first release.
